# 迁移边界与问题清单

> 本文依据 2026-11-28 仓库静态检查整理。“建议”是后续实施参考，本次未修改业务代码，也未确定最终 Unity 架构。

## 1. 需要替换的引擎耦合

### 配置资源

涉及 `CardSo`、`Effect`、`BuffSo`、`Condition`、`BattleSceneSO`，以及 `SO` 下的 `.tres`。

迁移时需要重新表达 Godot `Resource`、`[Export]`、纹理引用和资源间关联。Unity 侧可考虑使用 `ScriptableObject` 保存静态配置；当前的 `Dictionary<Effect, Array<float>>` 需要明确序列化方案，例如用可序列化条目列表保存效果和参数，再在运行时建立查询字典。不能只替换基类后假定 Inspector 会按原结构保存数据。

模板数值与运行时副本的分离值得保留；配置资源不应承担当前费用、Buff 剩余时长等局内状态。若后续需要存档、日志或“相同卡牌”判定，应补充稳定的卡牌/效果标识方案；现有代码只有资源对象身份。

### 纯逻辑与运行时对象

- `CardAttributeData` 已不依赖 Godot，可作为复用起点。
- `CardDataRuntime`、`EffectContext`、`EventBus`、`Trigger`、`NameBound` 和枚举含未使用的 `using Godot`，但其依赖类型仍需一起梳理，不能据此认定已经完全独立。
- `CardMono`、`Deck` 及牌堆派生类继承 `RefCounted`，本身没有节点行为，适合评估改成普通 C# 对象；无需因名字中有 `Mono` 就转换成组件。
- `DeckManager` 当前主要是集合操作，也可评估成为普通逻辑服务。只有承担场景装配和引擎生命周期职责的对象才需要组件化。
- `Deck.Shuffle` 需替换随机源，并明确是否要通过种子复现结果。
- `Godot.Collections.Array/Dictionary` 需替换或隔离；`EffectContext.Value` 的 `int` 与卡牌参数的 `float` 需统一约定。

### 场景、视图与输入

`Node`、`Control`、`Button`、`Label`、`TextureRect`、`ColorRect`、`PackedScene`、`_Ready/_Process`、`Pressed`、`NodePath`、`AddChild`、`Visible` 和物理处理开关都依赖 Godot。

Unity 侧需要重新搭建场景装配、卡牌视图、按钮入口、对象池及布局，并逐一重绑资源和控件引用。Unity 项目已包含 uGUI，但具体 UI 方案尚未在本次任务中确定。不要逐值复制旧场景的锚点、偏移和字号后就认为布局等价。

`DataChanged` 是普通 C# 事件，可保留这种通知方式，同时建立绑定、解绑和回收时的数据清理规则。Godot 的隐藏与禁用物理处理不等价于完整的对象池停用协议。

## 2. 原代码中已发现的问题

### 战场脚本：优先处理的编译与初始化问题

来源：[`BattleSceneMono.cs`](../../GameSystem/BattleSystem/BattleScene/BattleSceneMono.cs)、[`BattleSceneSO.cs`](../../GameSystem/BattleSystem/BattleScene/BattleSceneSO.cs)。

- `_Ready` 中 `Enemy = SceneData.PlayerPosition` 缺少分号。
- `ExchangePosition` 参数为 `position2`，方法体却访问 `Position2`，标识符不存在。
- `PlayerPosition` 为配置类的私有字段，却被另一个类直接访问。
- 两个文件使用 `List<object>`，但没有引入 `System.Collections.Generic`；所读项目文件也未启用隐式 using。
- `SceneData` 未导出、未赋值，也没有构造/注入入口；即使语法修正，仍可能空引用。
- 敌方列表错误读取玩家列表；直接赋值还会让场景运行时列表与模板列表共享引用。
- 索引检查只有 `position > Count`，没有拒绝负数和 `position == Count`。

这些是源码静态可见的问题，并非本次运行得到的错误日志。`List<object>` 配合 Godot 导出字段的可用性也需在原环境核实或在迁移时改为明确的数据结构。

### 牌堆：边界与一致性

来源：[`Deck.cs`](../../GameSystem/CardSystem/Deck/DeckData/Deck.cs)、[`DeckManager.cs`](../../GameSystem/CardSystem/Deck/Manager/DeckManager.cs)、[`Hand.cs`](../../GameSystem/CardSystem/Deck/DeckData/Hand.cs)。

- `DeleteCard(i)` 只接受 `i < Count - 1`，无法删除最后一张或单张牌；在某些牌堆数量下负索引会进入列表访问并抛异常。
- `DrawFromDeck` 在空堆返回 `null`，管理器仍把结果加入目标堆；按索引取牌失败时也会加入 `null`。
- 添加和转移没有统一的容量及有效性校验，无法保证失败操作前后状态一致。
- `CheckHandHold` 没有被调用，而且按卡牌总数计数，不符合当前“相同卡牌合并占手牌位”的规则。
- 弃牌锁区/活区和公共池只是数据声明，不能限制不合法流向。
- 非手牌接收方在每次转移后自动洗牌是当前代码行为，是否保留应依据玩法规则决定。

### 事件与效果：尚无执行闭环

来源：[`EventBus.cs`](../../GameSystem/CardSystem/Effect/EventBus.cs)、[`Trigger.cs`](../../GameSystem/CardSystem/Effect/Trigger/Trigger.cs)、[`NameBound.cs`](../../GameSystem/CardSystem/Effect/EffectNameBound/NameBound.cs)。

- `EventBus.Invoke` 直接索引字典，没有该时机的订阅列表时会抛异常。
- 遍历订阅列表时，如果回调增删同一列表，会使枚举失效；需要定义安全的发布期间修改策略。
- 可重复订阅同一触发器；没有统一清理时机或持续时间失效处理。
- `TriggerInvoke` 未检查 `_action`；未绑定回调就触发会空引用。
- `Invoke` 只接收时机，不接收当次上下文；没有把新事件数据传给触发器的机制。
- 效果函数映射为空，条件/持续时间未执行；配置、数值、目标、事件和处理函数还没有串联。

### UI 与描述：显示和回收问题

来源：[`StringMontage.cs`](../../GameSystem/Utils/StringMontage.cs)、[`UIPool.cs`](../../GameSystem/UISystem/UIManager/UIPool.cs)、[`CardUIBound.cs`](../../GameSystem/UISystem/UIBound/CardUIBound.cs)。

- 描述拼接遗漏最后一段，单段描述显示为空；测试卡恰好只有一段描述。
- 视图归还后仍持有卡牌数据并订阅事件，隐藏视图仍可能刷新，也会延长对象间的引用关系。
- 视图退出或销毁时没有解绑逻辑；设置新 `Data` 时才解除旧订阅。
- 重复归还同一个视图会让队列出现重复引用，后续申请可能取得同一视图两次。
- 数据设为 `null` 时 `Refresh` 直接返回，旧显示不会清空；回收也没有统一重置位置或交互状态。
- 动态描述尚未与运行时效果参数关联，无法仅靠刷新展示数值修正后的效果文本。

### 数值与配置封装

- `CardAttributeData.GetCurrent` 返回内部列表，调用者可绕过数值接口和变更通知直接修改内容。
- `CardDataRuntime` 构造时假定模板、效果字典与参数数组有效，没有空值或格式校验。
- `CardSo` 提供模板 setter，但模板变化不会同步既有运行时副本，也不会自动通知视图。
- 效果资源作为字典键，尚无跨序列化、存档或内容复制时的稳定身份约定。

## 3. 设计文档与源码的差距

以下是迁移时需保持可见的需求差距，不能靠更换引擎 API 自动补齐。

### 牌堆循环与卡牌池

[早期 v0.1](../CardSystem开发v0.1.md) 规划抽牌堆耗尽后自动洗回弃牌堆；[当前战斗生命周期](../card-system/02-战斗阶段卡牌生命周期.md) 明确已使用卡牌不会自动回到循环，必须通过特定手段恢复可用。

现有代码没有实现任一完整循环。后续实现应按当前战斗生命周期及 [Demo 范围](../develop/01-基础战斗Demo开发需求.md) 处理，不能因早期文档有此流程就默认加入自动洗回。

当前规则还要求相同卡牌合并占位、弃牌活区/锁区、公共保留池容量与流向、来源相关的溢出处理、回合末保留手牌以及逐张战斗结束结算，源码均未完整实现。

### 卡牌交互与角色

[v0.2](../CardSystem开发v0.2.md) 中的 `HandManager`、`HandCardView` 及悬浮、选中、取消、确认使用接口，在本次扫描的业务代码中不存在。当前卡牌场景只负责显示。

[v0.1](../CardSystem开发v0.1.md) 中的 `CardDefinition`、`CardInstance`、`CharacterDefinition`、`CharacterInstance` 是规划名称；现有实际类型是 `CardSo`、`CardMono` 等，没有相应角色实现。

### 探索与 Demo 范围

当前[探索规则](../card-system/03-探索阶段卡牌生命周期.md)采用常驻行动牌与个人物品卡；`OutDeckManage` 的抽牌堆字段不足以表达该规则。

三关 Demo 所需的关卡选择、木桩属性、胜利判定、奖励和战士天赋等也未形成程序模块。迁移与新增玩法应分别记录，避免对原项目完成度作出错误判断。

## 4. 建议的后续顺序

1. **先确定迁移边界与命名**：决定卡牌模板、实例、牌堆、效果与场景装配的职责，明确旧类型和新类型的对应关系；保留当前文档作为原始基线。
2. **迁移逻辑核心**：枚举、属性计算、卡牌运行时和牌堆操作。同步修正索引、空值及转移一致性问题，定义运行时身份和随机源。
3. **迁移配置及最小显示入口**：建立配置资产、示例卡、卡牌视图和对象池，在 Unity 中复现“按钮生成卡牌、费用改变后刷新、回收再绑定”的小闭环。
4. **接入规则与效果**：按当前设计补齐卡牌池流转、操作校验、效果处理函数与触发上下文；这一步包含原项目尚未实现的功能。
5. **补齐战斗流程**：角色、目标、能量、回合和胜负；再按 Demo 范围扩展关卡、奖励与天赋。
6. **最后清理 Godot 内容**：在 Unity 所需代码、配置和场景验证完成后，逐项核对旧资源引用与工程文件，再进行清理。

最小复现入口的验证应覆盖：卡牌实例数值互不污染模板/其他实例；费用通知正确刷新；单段/多段描述完整；池复用后旧卡牌不再驱动该视图；空牌堆及首尾/非法索引不破坏状态。更完整的牌堆和战斗验收再按当前设计补充。

## 5. 后续清理范围备忘

原工程位于仓库根目录，Unity 工程位于子目录 `FX113A1`。Godot 清理范围不止 `GameSystem`：还涉及根目录 `.sln/.csproj`、`project.godot`、主场景、按钮场景、`SO` 中旧资源以及各处 Godot 标识/导入文件。

清理前需要保留或转换仍使用的业务内容与美术引用；不能按文件夹名直接认定 `SO`、`ArtResource` 或 `icon.svg` 都可删除。本次未对 `ArtResource` 做全量迁移盘点。

还需核对根目录 Godot C# 项目的默认源码收集范围：Unity 项目嵌套在仓库中，现有 `.csproj` 未显式排除 `FX113A1`。继续向 Unity 项目添加脚本时，旧工程可能一并收集这些 C# 文件，产生跨引擎编译干扰。本次未执行构建，实际收集结果需在后续实施时验证。
